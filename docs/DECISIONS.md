# Decisions

Newest last. Each entry: what was decided, why, and what it costs.

1. **Next.js App Router with server actions, no separate API.** One codebase and one auth path; every action re-checks permission on the server. Cost: no public API for integrations yet.
2. **PostgreSQL via Prisma; local database from the `embedded-postgres` package.** No Docker on the dev machine. Production should use managed PostgreSQL. Dev DB `hifi_one`, test DB `hifi_one_test`.
3. **Permissions in the database, enforced by `requirePermission` on every page and action, with a test that fails when a guard is missing.** Roles are editable; `docs/ROLES.md` is generated.
4. **Accounting is double entry with exact decimals; posted lines are immutable (database trigger); corrections are reversals or credit notes.** Revenue is recognised on issue. Totals are per currency; only the consolidated reports convert.
5. **Brand colour follows the red H logo; primary actions are violet.** The original spec suggested blue/purple, which is available as a theme if wanted.
6. **Idempotency keys and row locks on payments and posting** so retries and concurrent users cannot double-post.
7. **Honest integrations.** Mail, ads, WhatsApp Business and AI show "not configured" until credentials exist; click-to-chat links are labelled as such.
8. **Employee monitoring is consent-gated and agent-based.** Policy version and acknowledgement per employee, visible status, screenshots with logged access, retention purge, a Windows console agent (`agent/`). No keylogging or covert capture. A signed installer and macOS/Linux agents are future work. See `docs/MONITORING.md`.
9. **Video meetings are peer-to-peer WebRTC (up to 8 people) with server-sent-event signalling in memory.** Zero extra infrastructure. Cost: no recording, strict networks need a TURN server, a restart ends live rooms. A media server is the upgrade path. See `docs/MEETINGS.md`.
10. **Contacts are the master record; leads and clients link to them and stay in sync.** Avoids duplicate entry across CRM, billing and meetings. Merge archives, never deletes.
11. **Interactive, gamified interface (owner request, after the first version).** Approved deviations from the plain reference: module-coloured icon chips, slide-over forms, a goals card on the dashboard, a navigation progress bar. (The pill tab strip and the sidebar level card were added and later removed, see 18.) Recorded in `docs/DESIGN_SYSTEM.md`.
12. **List screens share one pattern** (KPI strip, URL-based status chips, search, table, slide-over "New"). Filters in the address make views shareable.
13. **Per-user dashboard layout stored in `UserPreference` (JSON), validated against the widgets the person may see.** A widget a person lost access to is never shown or kept.
14. **Menu counts are cached 20 seconds per person** (`unstable_cache`) so the menu adds no per-page cost. Cost: they can lag slightly.
15. **The sidebar level card was removed** (see 18).
16. **Migrations are additive; folder names must sort after the latest.** Two were renamed after creation to fix ordering (databases updated to match).
17. **Production serving uses `npm run serve`; `npm run dev` is for editing only** (first visit to each page compiles it).
19. **Account block at the bottom of the sidebar; profile pictures.** At the owner's request the account menu and sign-out moved from the top bar to the bottom-left of the sidebar. Staff can add a picture (PNG, JPG, WebP, up to 2 MB) on My profile, and HR can set one for a colleague; it is a stored file of type USER_PHOTO, served by `/api/avatar/<id>` only to signed-in staff of the same organization, and shown wherever staff appear (initials when there is none). Clients and vendors see initials.
20. **Content calendar posts can go to several platforms and may have no client.** Own posts are approved by internal review; client posts still need client approval. Dragging a post to another day changes its date only (no new version). Nothing is posted to the platforms: a person marks it published.
21. **Home dashboard follows the owner's sample:** hero with period picker, quick actions, role-based tabs, needs-attention list and arrangeable cards. Every number comes from the same loaders as the reports (ledger balances, receivables aging, leads scope) so dashboard and reports cannot disagree; sections a role cannot see are not computed. The menu group "My Workspace" became "My Space" with items every employee has (profile, help, security, tasks).
22. **Arrange menu is per person and cosmetic:** stored in `UserPreference` (key menu), validated against the menu the person is allowed to see, never produces an empty menu. It is not an access control.
18. **Navigation lives only in the sidebar.** The owner asked to remove the top tab strip (it repeated the menu) and the Prospector level card at the bottom of the sidebar. Level, XP and daily goals stay on the dashboard. Menu count badges stay. Interactivity moved to motion and behaviour instead: fade-in on navigation, hover lift on link cards, whole-row click on tables.
23. **Agentify ERP is a benchmark, not a source.** Its interaction quality (complete UI kit, one list engine, confirmations, one feedback channel, event helper, flow tests, CI) is the bar; its code, schema, palette, font and domain are not copied. Hifi One keeps Next.js, Prisma, PostgreSQL, exact decimals with currency, and its brand. See `docs/REFERENCE_ERP_AUDIT.md`.
24. **Project knowledge lives in the repository.** `CLAUDE.md` holds the rules and the operating contract; `docs/SYSTEM_MAP.md`, `DESIGN_SYSTEM.md`, `DATA_MODEL.md`, `DATA_FLOWS.md`, `MODULE_STATUS.md`, this file and `REFERENCE_ERP_AUDIT.md` hold the detail; `.claude/rules/*.md` hold path-scoped rules. A change that alters architecture, a business rule or a module's status updates the matching file in the same change.

25. **Lists page by number in the address, 50 rows a page** (`src/lib/paging.ts`, `Pager`): shareable, works without client JavaScript, fits the `?status=` chips. Counts and KPIs are separate aggregate queries. Cost: one extra `count` per list; very large tables (audit log, monitoring) may later need cursor paging.
26. **Cross-module notifications live in `src/lib/events.ts`**, one function per business event, called by the action after the service commits, each with a dedupe key. Kept out of ledger transactions so a notification failure can never undo money. Cost: a crash between commit and notify loses that notification.
27. **Destructive and financial buttons use `ConfirmButton`** (native `<dialog>`). Cancelling an invoice and voiding a commission now require a reason, stored in the audit log (`src/lib/reasons.ts`). This adds a required input to two existing actions.

28. **Staff email is optional; the contact number is a second sign-in identifier.** `User.email` became nullable (never invented), `User.phone` holds the E.164 number, unique. A phone number only identifies the account; the password (and two-step code) is always required. Staff get setup links, never passwords chosen by someone else.
29. **One category list.** Campaign categories reuse `ServiceCategory` (the service catalog's list) instead of a second list; "SaaS" is the existing "SaaS Products and Subscriptions". Cost: campaign and catalog categories cannot diverge without splitting later.
30. **New permissions reach existing roles once**, when first registered, following the code defaults; afterwards the Roles screen owns each role. This let `campaigns.view` replace `crm.view` on the Campaigns page without locking anyone out.
31. **Initial records live in code (names, designations, roles, campaigns) and in a git-ignored file (numbers, CNIC)**, reconciled by an idempotent script that only fills gaps.

32. **Workfolio is browser-first and consent-based.** Snapshots come from a screen share the person starts and can stop; there is no covert capture and no live video feed for managers. A live view would need a media relay and explicit written consent.
33. **Client comments live in `TaskComment` with `internal = false`.** One table, one thread per task; the portal reads only non-internal comments on client-visible tasks of the signed-in client.
34. **Menu labels follow the business words:** "Customers" (was Client Accounts) and "Vendors" (was Vendor Directory); the record type is still `Client` in the database.

35. **Scheduled work uses the database as the lock.** One `JobRun` row per organization, job and day, plus a partial unique index allowing one RUNNING row, so any number of schedulers (button, command line, hosted cron, the optional in-process timer) are safe. A session advisory lock was rejected because connection pooling can release it from another connection. Closes the earlier open question about scheduling.
36. **Public endpoints are keyed or tokened, rate limited and answer uniformly.** `/api/jobs/run` needs `JOBS_TOKEN`; `/api/leads/capture` needs a per-source key whose hash is stored and shown once; `/sign/<token>` stores only the token hash. Lead capture answers alike for new and repeated leads.
37. **E-signature is a simple electronic signature.** It records typed name, optional drawing, time, address, browser and the fingerprint of the text. It does not verify identity. The text is frozen when sent and signing refuses if it no longer matches.
38. **Uploads fail closed when a scanner is configured.** With `CLAMAV_HOST` set, an unreachable scanner refuses the upload; with none set, files are stored and labelled not scanned. No simulated "clean".
39. **Time approval is informational.** Profitability counts all logged time; a rejection starts a conversation instead of silently changing costs. Nobody decides on their own hours.
40. **Client reports never carry spend.** The `campaign_client` report is built from a separate section list, tested to contain no spend, budget or cost words.
41. **One list engine, no client table component.** Paged lists stay server components: `src/lib/list-params.ts` parses the address, `src/lib/lists.ts` owns each list's filter (permission and record scope included) and its CSV export, and the kit's `Pager`, `SortTh`, `SearchBox`, `Chips` and `ExportLink` render it. A column-config `DataTable` was not added because rows mix links, badges and money per list; the shared parts are the filter and the controls. Exports stream every matching row in batches (no cap) and leave out sensitive fields (CNIC, bank details, audit before/after values, IP addresses). `csvCell` now leaves plain numbers (including negatives) unprefixed so amounts stay summable; anything else starting with `= + - @` still gets an apostrophe.
42. **Payroll pays approved commissions and bonuses.** A payroll run claims each person's `APPROVED` `CommissionEntry` rows in the run currency that no run holds yet (`payrollRunId`), adds them to gross as `PayrollItem.commission`, and withholds tax at the person's salary rate into `commissionTax` (included in `tax`; salary and commission are rounded separately so salary tax is unchanged). They were expensed at approval, so posting debits the payroll payable for that part instead of the expense account; paying the run marks them `PAID` with the run's payment entry. A claimed entry cannot be paid by hand; refreshing or deleting a draft run releases it. Entries for people with no salary structure in that currency stay on the commissions screen to be paid by hand. Before this, approved commissions were only paid by hand and were not taxed.

47. **New staff accounts need a verified email and an approver before they can sign in; CRM follow-ups run as timed sequences.** At the owner's request (2026-11-01, "an OTP mail when any employee/user is onboarded, it shall be sent for approval", "follow-up templates and workflows like in GHL"). Reading taken: an account made on the Staff Directory or Users screen gets an `OnboardingRequest`; the person receives a 6-digit code (24 h, 5 tries, only hashes stored) with a link to `/onboarding/<token>` where they enter it and choose a password; that sends the request to everyone with `onboarding.approve` (in-app and email); sign-in is refused with a clear message until it is `APPROVED`. The account stays `active` while pending (the existing setup link keeps working) because sign-in is blocked by the request, not by the flag; rejecting switches it off. The person who added someone cannot approve them unless they are a Super Admin, so a one-admin company still works. No email or no mail connection skips the code and goes straight to approval, marked unverified. Accounts made before this have no request and are unaffected. Follow-ups: a `FollowUpSequence` of `FollowUpStep`s (day offsets from enrolment) using `EmailTemplate` rows of kind `FOLLOW_UP`; new leads created after a sequence is switched on are enrolled by the runner, which also sends due steps (one unique `FollowUpSend` per step, so overlapping runners never double-send). It stops on a reply to any company mailbox, a stage change (optional), won, lost, converted or unsubscribe (signed link plus RFC 8058 one-click header; the address joins `SuppressedContact`). The runner is part of the `JOBS_AUTORUN` tick and `/api/jobs/run`, and `npm run followups:run`. Follow-ups have their own hourly allowance (`FOLLOW_UP_HOURLY_LIMIT`, default 150) so they never block invoices or resets. All system emails now go out as branded HTML with a plain-text part; built-in wording is editable per organisation (`EmailTemplate` row with the built-in key; reset deletes it). Cost: a pending person can be assigned work before approval; leads created before a sequence was switched on must be added by hand.

## Open questions

- Success feedback: `?ok=` query flag (current, visible in the address) or a short-lived flash cookie read by the layout?
- Scheduled work: decided (35), all three ways exist. Which one to use in production is a deployment choice (`docs/DEPLOYMENT.md`).
- Should commission accrue at payment time (inside `recordPayment`) instead of by the daily batch? (Payroll paying approved commissions: decided, 42.)
- Inline `"use server"` actions in pages vs `actions.ts` per module: standardise on `actions.ts` for new work?
43. *(Superseded by 46.)* **The public website is the original site's HTML, served by static route handlers under `/site`.** Rebuilding it in React would drift from the live look and mix its CSS with Tailwind and the ERP layout; serving each page as its own document keeps markup, styles and scripts faithful and needs no auth. Assets are self-hosted because of the CSP. Cost: pages are snapshots edited as HTML, and dynamic PHP parts (blog, job board, contact form, applicant accounts) are frozen, linked out or not yet wired. `scripts/site/` refreshes the snapshot.
44. **One domain for the website and the ERP; `/` decides per visitor.** At the owner's request hifimarketing.co serves both. `/` is a route handler (not a page, so the website HTML stays outside the ERP layout): first-run setup still wins, a valid session goes to `/dashboard`, anyone else gets the website home page at `/` with `Cache-Control: private, no-store` so a proxy never hands one person's answer to another. The ERP keeps its own paths (`/login`, `/dashboard`, `/portal`). Cost: `/` reads the session and the user count on every visit.
45. **The first-run setup token is optional.** The owner did not have the `SETUP_TOKEN` for the live server, so `/setup` now works without one: the token is checked only in production, only when `SETUP_TOKEN` is set and only when a value is entered. The lasting guard is unchanged: setup runs only while the database has no users (checked again inside the locked transaction), so it can never add a second administrator or reset an installation. Cost: until setup is finished, whoever reaches `/setup` first can create the administrator, so setup must be completed right after the first deploy.
46. **The public website is rebuilt as Next.js pages in its own route group, with its own scoped styles.** Superseding 43 at the owner's request ("completely revamp it, keep the assets"). The snapshot HTML carried ~1,800 lines of inline CSS per page, Font Awesome and a hero video that could not start until fully downloaded, and its contact and apply forms did nothing. Pages in `src/app/(site)/` keep the brand (HIFI blue, Inter, the same photos, video and copy) but share one header, footer, stylesheet scoped under `.hs` (so Tailwind and the ERP never see it) and content files, so a change is made once. The contact form becomes a CRM lead and the apply form a job application for HR (both in this app, so no public key is needed). Copy changes: the "We work with the world's top companies" strip naming Google, Apple, Tesla and others is replaced by the platforms the services actually use, and the frozen "posted N months ago" job dates are dropped. Cost: the roles and posts are still edited in code (`_content/`) until HR and marketing get screens for them.
49. **Commission rates per campaign, with a sales-manager share (2026-11-01).** At the owner's request each campaign or product has a commission rate per role (for example 3% digital marketing, 5% Agentify ERP subscription), set by finance on Commissions and shown to sales staff on My commissions. When a client pays, the agent who converted the client earns the converted lead's campaign agent rate, and the agent's manager (from the staff directory) earns the campaign's manager rate, each once per payment (`CommissionEntry` is unique on allocation and role). A campaign rate wins over a person's own rate; a campaign with no agent rate falls back to the personal rate, so existing behaviour is unchanged. Changing a rate only affects later payments. Commission is still worked out by the existing "Work out new commissions" batch after the payment is recorded, then goes through the same approve and pay steps; it is not computed inside the payment transaction (open question above).

48. **Client types and engagements (2026-11-01).** At the owner's request a client has a type (marketing and digital, software/app/AI, company incorporation, seller services, SaaS) and an allocated project manager. What a client bought is an `Engagement`: a retainer (recurring, quotas copied from the catalog plan's `PlanQuota` lines at the start, so later plan edits do not change it) or a single service order (one-time, quantity times unit price, one total quota). Quota usage is counted by hand in `QuotaUsage` (voidable, never deleted) per month for retainers, in total for single orders; going over a quota is shown, not blocked. MRR and ARR come only from active recurring engagements, per currency without conversion; one-time orders never count. Billing still runs through subscriptions and invoices; the engagement is scope, price and usage, so it is not a second invoice source. Interpretation: the ad platforms offered are the five named in the quota list; a plan simply leaves out the ones that are not enabled.
50. **Marketing delivery workflow (2026-11-01).** Built on the existing content calendar, meetings, projects and bonus entries rather than new parallel records. (a) A client's project manager (Client.projectManagerId) is the only person who can move that client's content from internal review to client review; the client then approves in the portal calendar and the social media manager schedules and publishes. Without a project manager the old rule (someone other than the author) applies. (b) A content entry carries a brief and sample link, and when it has an assignee and the client has an active project a project task is created and the assignee notified. (c) Publishing a post counts once against the client's active retainer quota for that kind of work (reel to reels, video or live to long videos, static, carousel or story to static creatives); it never blocks publishing. (d) Meetings have a purpose (discovery call, weekly review, support, tutorial, inquiry) and a recording link the host attaches. The ERP does not record video; recording needs a media server (docs/MEETINGS.md). (e) The customer success manager records one review per client per week (1 to 5 plus text). Finance sets rating tiers (for example 5 stars 5%); the highest tier reached sets a percent of the client's weekly retainer (annual recurring engagement value divided by 52), shared equally between the project manager and staff on the client's active projects as BONUS commission entries waiting for approval, unique per review and person. With no team the pool is zero. Interpretation: "rebate/bonus from that client's retainer" is paid out of the company's cost like any bonus; it is not deducted from the client's invoice.
51. **In-room meeting recording (2026-11-01).** Any meeting (team, progress, client, support) can be recorded by its host from the room. The host's browser composites the video tiles and mixes all audio, records with MediaRecorder and uploads 5 second chunks in order to one .webm under STORAGE_DIR/recordings (no media server, no new dependency). Limits: 16 MB per chunk, 1.5 GB per recording, one recording at a time per meeting. Every participant sees a persistent "being recorded" banner and the pre-join screen warns, so there is no covert recording. Only the host with permission `meetings.recordings` can start; watching and downloading need the same permission and are audited. Ending the meeting closes the recording; no chunks means FAILED. Interpretation: recording is host-side, so if the host's browser or network fails mid-meeting, what was uploaded so far is kept. New meeting type TEAM (team or progress meeting). Recordings live on the app server disk and must be backed up like other uploads.
52. **Project updates feed and phase (2026-11-01).** Software, app and AI projects get a dated updates feed (update, testing, release, blocker, decision) and one current phase (discovery, design, development, testing, client review, launched). Anyone with `tasks.edit` on a project they belong to can post; only `projects.manage` can move the phase. Each entry is internal or shown to the client; a project with no client never shows anything. Entries are hidden, not deleted. The client portal project page shows the phase tracker and visible entries only. Interpretation: the phase list is fixed, not configurable, and applies to any project, though it suits software work. Posting does not yet notify the client.
